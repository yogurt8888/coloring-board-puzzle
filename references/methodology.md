# 设计取舍与踩过的坑

给想理解实现、或准备改进它的人。**日常使用不需要读这篇。**

---

## 1. 问题与那条救命的不变量

规则：选画笔色 → 点一格 → 该格所在**整块连通同色区**变成画笔色，目标在全盘变某色。

关键不变量：**染色永远不会把一块连通区拆开** —— 一次操作只能把若干块"并起来"。
所以每块的状态只取决于它由哪些初始块组成，而不取决于合并顺序以外的细节。

这条不变量对搜索是决定性的：

- 朴素做法：状态 = 63 个格子的颜色串 → 4^63 种可能，深度 5 就跑不出来；
- 本项目做法：先按**初始连通块**（本项目 10~17 块）把棋盘压成向量，状态 = 每块当前色 → 4^17 量级，
  实际可搜索空间再小几个数量级。第 8 关从"跑不出来"变成 1.3 秒。

## 2. 为什么"一直点同一格"几乎总是最优

直觉：一直点同一格 ≡ 从该格做 Flood-It。每步都把"已占据区域"整体换色，
于是每步都能把贴边的同色块整片吞掉，雪球越滚越大。
而换来换去点不同格子，等于把已经攒起来的区域丢掉重开。

但要交付就得**证明**它真的最短，而不是"看起来最短"：

1. 先用同格法枚举出最短步数 `L`（按长度递增枚举颜色序列，一到 `L` 就停）；
2. 再用 BFS **只穷举 `≤ L-1` 层**：
   - 若 `≤ L-1` 层无解 → `L` 就是全局最短，同时得到了"最短性证明"；
   - 若 `≤ L-1` 层有解 → 说明同格法不是最优，中止并提示改走通用解。

只搜 `L-1` 层而不是搜满，是纯赚：省掉最贵的那一层（实测 15.4s → 1.3s），
结论一点没变（这一步改动做过 9 关全量回归，逐字比对）。

## 3. 两套独立实现

`solve_fast.py` 与 `crosscheck.py` 是**两套互不 import 的实现**：
前者在组件图上工作，后者直接对 63 个格子做洪水填充、枚举 `itertools.product(COLORS, repeat=L)`。

各自算「最短步数」和「可点格总数」，两者必须一致，否则立即中止。
这类互相对账在本项目抓到过两次真实漏报 —— 这是"只信一个脚本"最直接的代价。

## 4. 标定判据的演进（最曲折的部分）

从截图读棋盘 = 找出一串等间距的瓦片色格。看起来简单，实际迭代了四版：

| 版本 | 判据 | 栽在哪 |
|---|---|---|
| v1 | 数"长度像一格"的色段 | 棋盘最后一格右边是外框不是留白 → 必漏最右一列（把 9 列判成 8 列 / 直接失败） |
| v2 | v1 + 向四方向按格距扩展 | 能跑通，但靠"色段后面紧跟**近白**留白"筛候选 |
| v3 | v2 + 段颜色必须接近瓦片色 | 补掉了"背景凑巧成段"的假行（合成图上标题右侧背景段被当成格子，整盘上移一行、标成 9×8 却一路不报错） |
| **v4（现行）** | 种子行改用"最长等宽等距瓦片链"；扩展判据改成"把瓦片色段并成棋盘带 → 带要够长 **且** 带里还能分辨出格子" | —— |

**v3 的致命假设是"缝隙一定是近白留白"**：第 1~3 关的缝其实是**米色 (207,174,145)**，
这一条把所有候选段全否掉、标定直接失败。所以 v4 的判据刻意**与缝隙的颜色、宽度无关**。

v4 中间还走过一条弯路：想用"合并窄缝"消掉瓦片内部的高光带，
结果**缝里散落的 1px 杂点会顺着合并把两道真缝桥接起来**（第 3 关实测 4 个 1px 杂点桥掉 17px 真缝）。
正确做法是丢掉碎段 + 容忍多出来的段。

## 5. 交付图：为什么不能硬编码坐标

- 版面纵坐标会随**标题/副标题折行数**变化（实测偏 10px）；
- 面板数是按列算的，**最后一列常常少一个**（5 步 3 列时第 3 列只有 1 个面板）。

所以 `verify_render.py` 一律**从图里扫出**棋盘原点（逐列扫描瓦片色像素带），
而不是写死偏移；反查同时校验**圈**（圈色必须等于该步画笔色、圈心偏移 ≤ 6px）。

反查只能证明"画出来的图与提取出的棋盘自洽"，**证明不了提取本身对** ——
所以取色结果还要另外跟"逐行横扫颜色游程"对一次账。

## 6. 性能：瓶颈是往返次数，不是算力

实测：五个脚本合计 20.8 秒，而端到端交付要 5~10 分钟 —— 差额全是"一次跑一个脚本、
等输出再决定下一步"的多轮往返（单关 6~8 轮）。

所以优化顺序是：**先把链路并成一次调用**（`pipeline.py`），再谈算法。
算法侧只做了两处（BFS 只搜 `L-1` 层、crosscheck 两处纯剪枝），
单关就落到 1.3~3 秒；加上索引复用，已解关卡是 0.05 秒。

> 教训：想提速先量再改。一上来就去优化 BFS 是找错方向。

## 7. 坑清单（保持更新）

- 用 DFS / IDDFS + 全局 visited 会**误剪最短路径**，必须逐层 BFS + 全局去重。
- UTF-8 BOM 会让求解器少读一格 → 读 board 一律 `encoding="utf-8-sig"`。
- 「每步染色格数」的**末项不是终局格数**：它只算本次点击真正改色的格数，
  本来就同色的块会自动并片、不被计入（第 5 关末步 56 格但全盘 63 格变红）。
- 别用**缩略图**判断颜色或数格子（实测被坑三次：红读成黄、蓝圈看成红圈、"第 1 行全黄"看错）。
  要看细节就把那一处裁出来放大。
- 别把角色立绘、卡片、按钮附近的色块当棋盘格 —— 判据里必须有"等间距"这一条。
- 改 `recommend()` 的打分规则必须跑全量回归：它会静默换掉推荐路线，
  第 8 关就因此从 `12→26→35→49→61` 掉到 `11→20→22→46→60`（第 3 步几乎不长）。
